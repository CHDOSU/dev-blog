2026 AI 우왕톤("AI는 동료가 될 수 있을까?")에 45팀 **CJB.zip**으로 참가했습니다. 세 명이 약 3주 동안 **Safe Home**이라는 서비스를 만들었고, 오늘(11/15) 최종 제출을 마쳤습니다. 결과가 나오기 전에, 제가 맡았던 일을 **STAR**(Situation · Task · Action · Result) 기법으로 정리해 둡니다.

## 프로젝트 한눈에 보기

> **Safe Home, 안전한 첫 자취의 시작**
> 충북대 근처에서 처음 자취방을 구하는 대학생이 방을 비교하고, 계약 전에 확인할 위험 신호를 한 흐름으로 점검하는 서비스

- **왜 이 문제였나**: 국토교통부 실태조사(2025년 5월 기준)에서 전세사기 피해자 3만 400명 중 20~30대가 75.11%였습니다. 처음 계약하는 학생일수록 등기부, 특약, 전입신고 같은 기본 확인을 놓치기 쉽습니다.
- **주요 기능**
  - 문장으로 조건 검색 ("정문 10분 월세 40 세탁기 원룸") → Gemini가 조건을 읽고, 추천 점수는 규칙 기반으로 계산
  - 가상 계약서·등기 요약의 위험 신호 점검, 근거 법령과 확인 질문 안내
  - 국토교통부 실거래가로 주변 시세 비교
  - 실제 집을 스캔한 **3D 방 보기**
- **스택**: Streamlit(stlite), Gemini API, Vercel, Upstash Redis, model-viewer, KIRI Engine
- **팀 역할**: 기획·UI·발표자료(배정민), 개발·AI 연동·아카이빙(전수혁), 그리고 저는 **3D 스캔, 배포·인프라, 시연 영상**을 맡았습니다.

매물과 계약서는 모두 가상 데이터로 시연했고, 법률 자문이나 계약 안전을 보장하는 서비스가 아니라는 점을 화면과 발표에 명시했습니다.

## STAR 1. 172MB 3D 스캔을 휴대폰에서 열리게 만들기

### Situation

방을 고를 때 사진만으로는 공간감을 알기 어렵다는 이야기가 나와서, 실제 집을 3D로 스캔해 "방 안에 들어가 보는" 경험을 보여 주기로 했습니다. 처음엔 Scaniverse로 찍은 2.4MB 모델을 쓰고 있었지만 품질이 아쉬웠습니다.

### Task

KIRI Engine으로 새로 스캔한 집을 **휴대폰 브라우저에서도 부드럽게** 보여 주고, 스캔에 찍힌 **사람이 드러나지 않게** 처리해야 했습니다. 제출 하루 전이라 시간도 빠듯했습니다.

### Action

- KIRI에서 내보낸 원본 GLB는 **172MB, 약 200만 면, 4096px 텍스처**였습니다. 텍스처가 깨지지 않는 선에서 면 수를 **약 25만 개**로 줄이고, 텍스처를 **2048px WebP**로 바꾸고, 좌표를 압축했습니다.
- 처음엔 3D 가우시안 스플랫인 줄 알았는데, 실제 파일은 일반 메쉬(GLB)라는 걸 확인하고 기존 model-viewer 코드를 그대로 재사용했습니다.
- 밖에서 보면 스캔 가장자리가 지저분해서, 방 중심과 바닥 높이를 계산해 **방 한가운데 눈높이 시점**(시야각 85°, 위아래 회전 제한)을 기본으로 하고 「방 안에서 / 밖에서」 전환 버튼을 넣었습니다.
- 스캔에 찍힌 사람 2명의 위치를 3D 좌표로 찾아 **그 부분 텍스처만 모자이크**했습니다.
- 화면에 "실제 집을 스캔한 시연용 모델이며, 추천 매물의 실제 방과 다릅니다"라는 안내를 넣고, 촬영 공간의 공개 동의를 받았습니다.

### Result

- **172MB → 5.6MB** (약 97% 감소). 실제 아이폰에서 회전·확대가 정상 동작하는 것을 확인했습니다.
- 계약 점검 화면에 들어가면 3D 방이 바로 보이는 흐름이 팀 리뷰에서 좋은 반응을 얻었습니다.
- 기둥에 너무 가까이 가면 화면이 하얗게 되는 문제는 남았고, 한계로 기록해 두었습니다.

## STAR 2. 마감 당일, 제출물 7개를 빠짐없이 내기

### Situation

제출 마감은 11/15 18:00였고, 늦으면 항목마다 감점이었습니다. 최종 제출 폼, GitHub 저장소와 커밋 해시, 배포 링크, 발표 자료, 시연 영상, Notion 페이지, 아카이빙 자료까지 **7개**를 준비해야 했습니다.

### Task

저는 **시연 영상 제작**과 **배포·Notion 공개 상태 점검**, 그리고 애매한 제출 규칙을 **운영진에게 확인**하는 일을 맡았습니다.

### Action

- **시연 영상**: 규칙(5분 이내, 자막·음악 금지, 결과 조작 금지)에 맞춰 제출 버전에서 실제로 동작하는 기능만 찍었습니다. 문장 검색 → 추천·더보기 → 계약서 점검 → 미확인 체크리스트 → 3D 방 보기 → "계약 위험 매물 제외" 검색 순서로 구성하고, 앞뒤만 잘랐습니다.
- **배포 점검**: Vercel 운영 배포가 동결한 main 커밋과 일치하는지 확인하고, 문장 검색·추천·계약 위험 표시·AI 특약 설명·미확인 체크리스트 화면을 직접 눌러 봤습니다.
- **공개 범위 점검**: 심사위원이 볼 Notion 팀 홈과 하위 페이지·DB를 시크릿 모드로 열어 확인했습니다. 공공데이터포털 키를 적어 두었던 페이지는 삭제하고 키가 노출되지 않았음을 확인했고, 잡담이 섞인 회의 받아쓰기 원문도 정리했습니다(프로젝트 관련 내용은 회의록에 따로 보존).
- **규칙 확인**: 저장소 이름 규칙(`WOOWANGTHON_TEAM_{번호}_{FE/BE/AI/ETC}`)과 실제 저장소 이름이 달라서 운영진에게 문의했고, 접미사 없이 제출해도 된다는 답을 받아 팀에 공유했습니다.

### Result

- 시연 영상은 **2분 48초**, 배속·자막 없이 완성해 업로드했습니다.
- 7개 제출물을 모두 준비했고, 아카이빙 자료는 GitHub Actions의 **Validate Archive Submission**까지 통과했습니다.
- 키 같은 민감 정보가 공개 페이지에 남지 않은 상태로 제출할 수 있었습니다.

## 실수에서 배운 것: 올리기 직전에 최신 main 확인하기

11/14 오후, 3D 모델을 올리면서 `app.py`와 README도 같이 올렸는데, 제 파일은 팀원이 **7분 전에 수정한 버전보다 이전 기준**이었습니다. 결과적으로 팀원의 수정(AI 검색 실패 안내, README 재작성)을 덮어써 버렸습니다.

저장소 쓰기 권한 문제로 GitHub 웹 업로드를 쓰고 있었던 터라 Git이 충돌을 알려 주지 못했습니다. 바로 알아채고 팀원 수정 위에 3D 변경만 다시 얹어 복구했고, 그 뒤로는 **업로드 직전에 최신 main을 다시 확인**하는 걸 원칙으로 삼았습니다. 짧은 해커톤일수록 "빨리 올리기"보다 "덮어쓰지 않기"가 중요하다는 걸 배웠습니다.

## 돌아보며

- **AI는 정말 동료였다**: 팀 전원이 Claude, Codex 같은 AI 도구로 개발했고, 무엇을 AI에게 맡겼는지 Notion의 "Agent 활용 기록"에 남기고 사람이 검토했습니다. 3D 최적화, 배포 점검, 회의록 정리처럼 손이 많이 가는 일을 AI와 나눠 하면서도, 최종 확인은 직접 하는 습관이 중요했습니다.
- **한계를 숨기지 않기**: 가상 데이터, 과거 실거래가, 규칙 기반 판정의 오판 가능성, IP 기반 제한의 우회 가능성까지 발표에 그대로 적었습니다. 할 수 있는 것과 없는 것을 구분해 말하는 게 오히려 신뢰를 준다고 느꼈습니다.
- **다음에 해 보고 싶은 것**: 동의를 받은 실제 매물의 실내 스캔을 해당 매물에만 연결하는 것, 그리고 계약서 사진을 기기 안에서 OCR로 읽어 개인정보를 밖으로 보내지 않는 구조입니다.

결과가 나오면 후기를 이어서 올리겠습니다. 함께한 정민, 수혁 님 고생 많으셨습니다! 🚀
